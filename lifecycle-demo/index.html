        How this was built — the 4D method, applied

        The demo isn't a mock-up of a chat window; it's a set of deliberate product decisions made visible. Each phase below names the frameworks used and links to the moment in the demo where the decision shows up. The rules themselves live in shared/ — the same modules that compile into the agent demo's system prompt.

        "Tandem's core product problem is earning the right to be stateful: every remembered fact, re-entry moment, and proactive nudge either compounds trust or destroys it."

        • Persona: the mass-affluent / workplace-plan customer with no human advisor — an access-expansion play, not a high-net-worth upsell. Jobs-to-be-done framing: "When I worry about money (weekly), I want a plan that knows me, so I stop feeling behind" — tested against the non-AI baseline (static planning tools) before assuming AI is the answer.
          • Journey stages: Get Oriented → Plan → Act → Stay on Track. Listing activities per stage exposed the core insight: financial guidance is twenty conversations across months, not one session. That's why "re-entry moments" are a first-class design object.
          • Pain sizing: magnitude (millions underserved), frequency (worry is weekly, advisor contact yearly), severity (retirement adequacy), competition (Schwab Portfolio Insights, Robinhood Cortex, BofA Erica, ChatGPT personal finance), contrast (robos act for you without explaining; chatbots explain without knowing you — the wedge is the middle).
          • Impact × feasibility converge: v1 = orientation + plan check-ins (read-only, verifiable, low blast radius). Not trade execution. Feasibility in finance = "can the intelligence do this compliantly."
          • SOUR expectation audit: stakeholders expect sci-fi accuracy and contextual awareness; today's reality demands verification affordances and explicitly supplied context. The gap is a design deliverable, not a footnote.

        • Stateful conversation design: four explicit states (orientation / planning / action / escalation) with designed transitions — visible in the header pill. Not one open-ended chat. The machine is shared/states.js.
          • Sheridan autonomy per action: guidance & education at levels 1–4; pre-filled changes at level 5 (execute only on approval); level 6+ prohibited — never auto-execute financial actions. The action card is this decision rendered as UI (shared/guardrails.js).
          • HiTL with verification access: every cited figure is tappable back to its source (📎). Explainability = showing verifiable evidence, never asking the model to narrate its reasoning (LLMs fabricate rationales — SOUR observability).
          • Memory strategy: three types (explicit / derived / behavioral), per-type decay, scope boundaries, and consent before derived or behavioral memory is used — implicit extraction, explicit transparency (shared/memory.js). User view/edit/delete is table stakes in finance. The uncanny-valley guard: a coach that misremembers your risk tolerance is worse than one that remembers nothing.
          • Re-entry moments: session bridges ("last time we decided…"), Fogg-timed nudges (fire at high-motivation moments — a volatility login is one — and make acting nearly effortless), graceful cold starts.
          • Compliance-to-UX translation: refusals designed as trust-builders — explain why, then redirect to what's in scope. Disclosures as conversational moments, not legal walls. FINRA applies existing communications rules (Rule 3110 supervision, recordkeeping) to chatbots — so every message is designed as a retail communication, retained and supervisable.
          • Safety by design: limitations stated up front, degradation cues (outage = disabled state, not improvisation), easy feedback, constrained inputs.
          • Accessibility as a design invariant: WCAG 2.2 AA is scoped in from the start, not retrofitted — streamed replies announced on clause boundaries in a polite live region, every citation a real disclosure, no blocking browser dialogs, and the rules themselves version-controlled in .claude/rules/accessibility.md.

        • Platform AI owns the model; the UX lead shapes what "good" means and proves it.
          • Golden dataset first: human-verified (question, expected behavior, expected sources) cases, version-controlled in evals/golden.json, started before build — it gates every later change and is the shared language with risk. Run them: npm run evals.
          • RAG for facts, never fine-tuned facts: plan documents, fund data, and policy content retrieved with citations; the RAG Triad (context relevance / groundedness / answer relevance) surfaces in the UI as tappable sources — an eval metric turned into a user-facing trust affordance.
          • Faithfulness target ≈ 1.0 on cited figures (0.9 is a floor elsewhere; not in finance). Numbers come from calc tools, not model arithmetic.
          • Model graders output labels, not scores: COMPLIANT_REFUSAL / NEEDS_REVIEW / VIOLATION — visible in presenter mode on the stock-tip refusal.
          • Red teaming as first-class UX work: jailbreak-to-stock-tip, PII probes, out-of-scope advice (tax/legal/medical), distressed-user scenarios — multi-turn attacks, private adversarial sets, calibrated judges before they gate releases.
          • Eval-driven releases: five-case minimum per conversation state (happy path + 3 edges + 1 boundary) written before build; expected pass rates gate each release.
          • Accessibility is an eval tier, not a checklist: live-region attributes, accessible names, focus-visible rules and the ban on blocking browser dialogs are machine-checked in the same suite that gates policy — cheap regression gates for the parts that are mechanizable.

        • The 2026 reality check: fully autonomous agents are ~2–3% of production workloads. The winning architecture is a deterministic workflow that delegates to agents only where reasoning is required — which preserves the audit trail compliance needs.
          • Build/don't-build honesty: Tandem scores "build" on complexity and scale but "don't build" on environment constraints (errors are costly in finance) — which is exactly why autonomy is capped at propose-and-confirm and why a compliance-verifier agent cross-validates the strategy agent.
          • Memory boundaries between agents: the budgeting agent sees task context only; the user-visible profile is the shared layer. A UX decision, not just architecture.
          • Failure design: wrong balance shown = incident; market-crash day = peak load + peak anxiety (the worst time to fail — degrade to disabled states); abuse vectors closed (rate limits, scoped prompts — your coach is not free GPT access).
          • Analytics drive evolution — see the Metrics tab: quality signals → weekly golden-set triage → eval-gated releases → Sheridan-level promotions per state. Containment is not the goal: in finance you want some escalations, and "appropriate escalation" is counted as success. Industry benchmark context: new assistants contain 35–50%, mature ones 65–80% — but low CSAT with high containment means you're exhausting customers, not helping them.
          • See it running for real: the agent demo is the same shared core driven by a live model — server-enforced confirmation gating, tool-sourced numbers, real telemetry.
